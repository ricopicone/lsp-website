# Design note — Workgroup-primary Events (the reframe)

**Status:** proposed, awaiting Rico's sign-off (2026-05-31). Companion to
`docs/design-workgroups.md`. A **stopgap is already in place** (Event's
workspace kind now follows its `event_type`) so reading groups aren't broken
while we settle this.

## The problem

The current `Event ⇄ Workgroup` link is **Event-primary and vestigial**: an
`Event` optionally *attaches* a `Workgroup` (`Event.workgroup` OneToOne;
`Event.get_or_create_workgroup()` mints one as an afterthought). That's left
over from the calendar-first start. It produces real gaps:

- Nothing creates `reading_group` (or other) workgroups except an Event making
  one — so the per-kind directories sit empty.
- "Cartel" exists twice (an `Event.Type.CARTEL` *and* a `Cartel` workgroup).
- A group's durable identity (members, channel, works, files) is modeled as a
  side-effect of a calendar Event, which is backwards.

## The principle

**The Workgroup is primary; an Event is a scheduled / registerable (or
private) occurrence that a Workgroup generates.** Every Event has a
*generating workgroup* — the group responsible for it:

| Event kind | Generated by | Notes |
|---|---|---|
| Seminar / Reading group / Cartel (annual-program offerings) | **their own** Workgroup (`kind=seminar/reading_group/cartel`) | the offering *is* the group; the Event is its term offering (schedule + pricing + registration). Roster = registrants + faculty. |
| Special Event / Day of Assembly / Working Day / Scholarly Seminar | the **Programming Committee** workgroup (or relevant committee) | the PC organizes them; the Event carries its own public/members audience. The workgroup link is *provenance/ownership*, not the roster. |
| Committee / Working-group meeting | that **committee / working group** workgroup | a **private** Event, visible to the group's members. |

So `Event.workgroup` means **"the workgroup that owns/generated this event."**
For offerings that's the offering's own group; for organized events it's the
organizing body.

## Model changes

- **`Event.workgroup`: OneToOne → ForeignKey** (nullable). A group generates
  many Events over time — e.g. a reading group that runs each academic year is
  one Workgroup with one Event per year (which lines up with the existing
  per-year `Program`). A committee generates many meeting Events.
- **`event_type` stays on Event** (it's the occurrence's nature). It no longer
  needs to "agree" with `workgroup.kind`, because the workgroup may be the
  *organizer* (PC) rather than the offering. For offering-type events,
  `event_type` and the generating workgroup's `kind` do coincide.
- **`Event.get_or_create_workgroup()` is replaced** by the inverse:
  `Workgroup.generate_event(...)` (or the PC-admin "schedule this group for AY
  20XX" flow). The current method becomes the stopgap-only path and is removed
  once creation is inverted.
- **Roster semantics are unchanged** from Stage 5: for offering workgroups,
  `is_member` derives from faculty + paid/comped registrants; for
  committee/WG workgroups it reads `WorkgroupMembership`. `is_member` already
  dispatches on the attached event, so this still holds.

## What it cleans up

- Reading groups (and every annual-program kind) get a real creation path →
  the `/groups/<kind>/` directories populate from actual data.
- The cartel double-notion collapses: a cartel is a `Workgroup`; its public
  sessions are Events it generates.
- Special events / assemblies / work days gain a clear owner (the PC), so they
  can surface under the PC's workspace and on the members calendar.
- `Event.get_or_create_workgroup` (the vestigial attach) goes away.

## Migration (the load-bearing part — on prod data)

Registration, pricing, the PC admin, and the calendar all assume Event-primary,
so this is bigger than a Stage. Plan:

1. `Event.workgroup` OneToOne → FK (additive-ish; the column already exists).
2. **Backfill existing prod Events** (2025-26 / 2026-27 seminars, etc.): create
   or find a generating Workgroup for each and link it. Annual-program events →
   an offering workgroup; special/assembly/work-day events → the PC workgroup.
3. Invert creation in the PC admin: create/seed a **Workgroup**, then generate
   the term's Event under it.
4. Remove `Event.get_or_create_workgroup`; keep `can_edit_event` /
   `is_program_committee` (already workgroup-roster based).

Take an RDS snapshot before the backfill, as with the committee fold-in.

## Open forks (settle before building)

1. **Recurring offerings:** does a seminar/reading group that runs in multiple
   years share **one Workgroup across years** (one identity, many yearly
   Events) or **one Workgroup per offering/year**? → *(Recommend: one shared
   Workgroup across years — that's the point of a durable group; the Program +
   Event carry the per-year specifics.)*
2. **Organized events** (assembly / work day / special): do they get a
   **dedicated workgroup** each, or just point `Event.workgroup` at the **PC**
   as generator (no new group)? → *(Recommend: PC as generator; no dedicated
   group unless one genuinely collaborates.)*
3. **Committee/WG meetings as Events:** in scope for this reframe, or a later
   follow-on once offerings are inverted? → *(Recommend: model the FK to allow
   it, build the meeting-creation UI later.)*

## Stopgap currently in place

`Event.get_or_create_workgroup()` maps `event_type → Workgroup.Kind`
(seminar→SEMINAR, reading_group→READING_GROUP, cartel→CARTEL; others default to
SEMINAR). This keeps the per-kind directories correct in the interim. It is
**removed** when creation is inverted per this note.
